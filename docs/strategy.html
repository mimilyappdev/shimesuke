💡 全体思想

フリーランスクリエイターの仕事フロー「見せる → やりとりする → こなす」を、3つのシンプルなツールで一気通貫にカバーする。

MiteOrder　ポートフォリオ＋見積もり。依頼者が作業内容を選んで送る。
↓ 依頼が届く
EasyReply　やりとり管理。テンプレで返信・調整・受注確定。
↓ 確定したら自動追加（任意）
〆スケ　納期・フェーズ管理。締切順に案件を一覧表示。

〆スケ単体のターゲット：

締切のある人なら誰でも。フリーランス・学生・社会人・同人作家など職種問わず。

3アプリ連携のターゲット：

コミッション（受注制作）をこなすフリーランスクリエイター。DM・Skeb・CONNALAE等の複数窓口で依頼を受ける人。

アプリ思想・コンセプト
〆スケ
SchedulEX		 「締切がある人なら誰でも使える」案件・納期管理ツール。
フリーランス・学生・社会人・同人作家など職種・業種を問わない。TODOアプリでもカレンダーアプリでもなく、「締切順に並ぶガントカレンダー」という独自のポジション。シンプルさを最優先。
MiteOrder
ミテオーダー		 「見て、選んで、見積もり依頼ができる」クリエイターの受付窓口。
クリエイターが自分のポートフォリオ＋料金表を1ページで公開。依頼者は登録不要で作業内容を選び、合計金額を確認してそのまま送れる。SNSのDMや口頭で値段を聞かせる手間をなくす。
EasyReply
ラクリプ		 「毎回一から書かなくていい」依頼やりとり管理ツール。
初回返信・見積送付・修正対応・納品など、フェーズごとに返信テンプレを管理。差し込み変数（{{price}}等）で毎回カスタマイズも最小限。将来的にMiteOrderからの依頼を受け取り、受注確定→〆スケ連携のハブになる。
RakuThrough
ラクスルー		 「創作活動するあなたに確定申告ラクスルー！」収支管理ツール。
青色申告対応。Booth・Skeb等「売った日≠入金日」の売掛管理が特徴。棚卸し・減価償却・申告サマリーまでカバー。3アプリとは別Firebaseプロジェクトのため自動連携はなく、受注確定後の売掛登録は手動。

クリックでコピー # フリーランスクリエイター向け 3アプリ連携設計の相談 ## 作っているものの全体像 フリーランスクリエイター（イラストレーター・デザイナー・VTuber素材クリエイターなど）向けに、受注〜納品の仕事フローを丸ごとカバーする3アプリを個人開発しています。 ### アプリ一覧 **1. MiteOrder（ミテオーダー）** クリエイターが自分のポートフォリオ・料金表を公開し、依頼者がその場で見積もりを選んで送れるページ。 - 現状：静的HTMLのデモページのみ。Firebaseなし。 - 依頼者がチェックボックスで作業内容を選ぶと合計金額が出て、フォームで送信できる。 - 依頼者は登録不要。クリエイターが自分のページを持つイメージ。 **2. EasyReply（ラクリプ）** クリエイターが依頼者とのDM・メールのやりとりを管理するツール。返信テンプレートを管理し、フェーズ（初回返信/見積送付/修正対応/納品）ごとに使い分けられる。 - 現状：テンプレートのUIのみ実装済み。Firebaseなし・localStorage。 - 将来：依頼ごとにスレッド管理・受注確定ボタンを追加予定。 - 価格：買い切り（将来サブスクへ） **3. 〆スケ（SchedulEX）** 依頼の締切・作業フェーズを一覧管理するガントカレンダーツール。 - 現状：Firebaseあり（Google認証・Firestore同期済み）。稼働中。 - 全案件を1ドキュメントにまとめてFirestoreに保存（users/{uid}/schedulex/data）。 - 価格：Free（3件まで）・Pro買い切り（Booth）・サブスク（Firebase同期） ### 別アプリ（連携非対象） **RakuThrough（ラクスルー）** 収支・帳簿管理ツール。売掛・経費・クレカ明細などを管理。 - 別Firebaseプロジェクトのため、3アプリとの自動連携は難しい。受注確定後は手動入力で割り切り予定。 --- ## 共通インフラ - Firebaseプロジェクト: mimilyapp（東京リージョン） - 3アプリすべて同一プロジェクトに入れる予定 - 認証: Google認証・同じuidを共有 - Firestore構造: users/{uid}/ 以下にアプリごとのサブコレクション --- ## やりたいこと（連携フロー） ``` 依頼者がMiteOrderで作業内容を選んで送信 ↓ Firestoreに見積もり依頼を保存 ↓ クリエイターがEasyReplyで依頼を確認・やりとり・受注確定 ↓（受注確定ボタンを押したとき） ├─ 〆スケ に案件を自動追加（任意ON/OFF） └─ RakuThroughには手動入力（別プロジェクトのため） ``` --- ## 現在検討中のFirestoreスキーマ（案） ``` users/{uid}/miteorder/requests/{requestId} clientName: string // 依頼者名 items: [{id, name, price}, ...] // 選んだ作業内容 totalMin: number // 合計金額（最低額） notes: string // 備考・参考URL等 status: ??? // ← ここが相談したい createdAt: timestamp ``` --- ## 相談したいこと **statusの設計について意見をください。** 現在の案: `"pending" | "negotiating" | "confirmed" | "declined"` - pending: 依頼が届いた（未対応） - negotiating: やりとり中 - confirmed: 受注確定 - declined: お断り ### 具体的に聞きたいこと 1. この4段階で実用上足りるか？追加すべきステータスはあるか？ 2. フリーランスクリエイターの実務でよくある「保留」「一時停止」「キャンセル（確定後）」などは別ステータスにすべきか？ 3. 〆スケへの自動追加は "confirmed" のタイミングでよいか？それとも別のタイミングが適切か？ 4. EasyReplyがMiteOrderのFirestoreドキュメントを更新する設計は適切か？（セキュリティ・設計観点から） ### 前提・制約 - 個人開発・シンプルさ優先 - 最初は日本国内のフリーランスクリエイターが対象 - 将来的に英語対応・海外展開も視野あり - 複雑なワークフロー管理ツールにはしたくない。あくまでシンプルに。
